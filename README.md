# 🎯 Memecoin Sniper Bot

Телеграм-бот для снайпинга мем-токенов в сетях **BNB Smart Chain** и **Robinhood Chain**
(и в любой другой EVM-сети с Uniswap V2-совместимым DEX — достаточно дописать её в конфиг).

У каждого пользователя свой кошелёк внутри бота: его можно пополнить, вывести с него
средства и экспортировать приватный ключ. Приватные ключи хранятся зашифрованными
(AES-256-GCM, ключ выводится из `MASTER_KEY` через scrypt).

> ⚠️ **Риски.** Снайпинг новых токенов — крайне рискованное занятие. Большинство свежих
> пар оказываются скамом. Бот делает всё, чтобы отсечь honeypot и высокие налоги, но
> **гарантий не даёт никто**. Держите на кошельке бота только те деньги, которые готовы
> потерять.

## Возможности

**Кошелёк**
- отдельный EVM-кошелёк для каждого пользователя, создаётся автоматически при `/start`;
- один адрес для всех EVM-сетей бота, балансы по каждой сети;
- уведомление о каждом пополнении (фоновый наблюдатель сравнивает баланс);
- вывод средств на любой адрес (частично или «всё» — с учётом газа);
- экспорт приватного ключа для импорта в MetaMask/Trust Wallet.

**Снайпер**
- работает и с **Uniswap V2**, и с **Uniswap V3**: слушает `PairCreated` у V2-фабрик и
  `PoolCreated` у V3-фабрик, ловя новые пулы в момент листинга;
- при ручной покупке сам выбирает самый ликвидный пул токена среди всех площадок сети
  (V2 и все тиры комиссий V3);
- ждёт залива ликвидности, затем проверяет токен и покупает — всё автоматически;
- лимиты: максимум открытых позиций и максимум покупок в час;
- ручная покупка: пришлите боту адрес токена, получите карточку с проверками и кнопками.

**Перехват разгона (не только новые токены)**
- следит за уже торгующимися пулами и покупает те, где начинается движение:
  цена подросла, сделок много, покупок заметно больше продаж;
- верхняя граница роста не даёт зайти на вершине пампа;
- наблюдение стоит один `eth_getLogs` на сотню пулов — тяжёлые проверки
  запускаются только для кандидатов;
- `/trending` показывает текущий рейтинг, `/watch` добавляет токен вручную.

**Проверки безопасности (анти-rug)**
- **симуляция покупки и продажи** через `eth_call` со `state override`: бот реально
  «прогоняет» сделку на ноде, не тратя газ — одинаково для V2 и V3;
- перед отправкой каждая транзакция проверяется `eth_call`: доказано провальная
  сделка не отправляется и не жжёт газ;
- **honeypot**: если продажа в симуляции не проходит — токен не покупается;
- **реальные налоги** на покупку и продажу: двоичный поиск по `amountOutMin` даёт
  фактически получаемую сумму, точность 0.1%;
- ликвидность (минимум и максимум), доля сожжённого LP, отказ владельца от прав
  (`renounced`), лимиты `maxTx`/`maxWallet`, чёрный список токенов.

**Позиции**
- тейк-профит (в т.ч. частичная фиксация), стоп-лосс, трейлинг-стоп;
- монитор пересчитывает стоимость позиций и продаёт по правилам без участия человека;
- ручная продажа 25 / 50 / 100 %, история сделок и суммарный P&L.

## Быстрый старт (терминал)

```bash
git clone https://github.com/gytfel/mem-robinhood-and-bnb.git
cd mem-robinhood-and-bnb

python3 -m venv .venv && source .venv/bin/activate
pip install -e .          # появится команда sniper

sniper init               # спросит токен бота, сгенерирует MASTER_KEY, создаст .env
sniper doctor             # проверит ключи, Telegram и ноды
sniper run                # запуск
```

Дальше отправьте боту `/start` — он создаст кошелёк и покажет адрес для пополнения.

### Команды CLI

| Команда | Что делает |
|---|---|
| `sniper init` | создаёт `.env` и `MASTER_KEY` (`--force` — перезаписать) |
| `sniper doctor` | проверяет ключи, Telegram, каждый RPC и поддержку симуляции сделок |
| `sniper run` | запускает бота (`--log-level DEBUG` — подробные логи) |
| `sniper check 0xТокен` | полная проверка токена прямо в терминале |
| `sniper discover 0xРоутер` | определяет версию DEX (V2/V3), достаёт фабрику и WETH; с `--quoter` и `--token` проверяет адреса настоящей котировкой |
| `sniper wallets` | пользователи, их адреса и балансы |
| `sniper keygen` | печатает новый `MASTER_KEY` |

Общий флаг `--env-file /путь/к/.env`. Без установки пакета работает
`python -m sniperbot <команда>`.

## Запуск на сервере (24/7)

```bash
ssh root@ВАШ_IP
apt update && apt install -y git
git clone https://github.com/gytfel/mem-robinhood-and-bnb.git
cd mem-robinhood-and-bnb
ls scripts/install-server.sh          # нет файла? git checkout claude/memecoin-sniper-bot-1nkbtm
sudo bash scripts/install-server.sh
```

Скрипт поставит Python и зависимости, создаст пользователя `sniper`, установит
бота в `/opt/memecoin-sniper`, спросит ключи, зарегистрирует systemd-сервис и
запустит его. Дальше:

```bash
systemctl status memecoin-sniper      # состояние
journalctl -u memecoin-sniper -f      # логи
systemctl restart memecoin-sniper     # после правки .env
bash scripts/backup.sh                # бэкап базы кошельков
```

### Обновление

**Настройки в `.env` не теряются и не отстают.** Обновление никогда не
перезаписывает этот файл — там ключи и `MASTER_KEY`. Но новые настройки в нём
появляться должны, иначе файл молча отстаёт от версии: настройка добавлена, а
человек о ней не узнает. Поэтому `deploy.sh` и `update.sh` дописывают
недостающие ключи **в конец файла**, с пустыми значениями и комментариями из
`.env.example`. Существующие строки не трогаются вообще, а рядом остаётся
`.env.bak`.

Вручную — то же самое:

```bash
sniper env-sync --dry-run     # показать, что добавится
sniper env-sync               # дописать
```


Обновление запускается **из клона репозитория** (там, где лежит `.git`), а не из
`/opt/memecoin-sniper`: в `/opt` копия кода без истории git, обновлять её нечем.

```bash
cd ~/mem-robinhood-and-bnb            # каталог, куда клонировали репозиторий
sudo bash scripts/update.sh
```

Скрипт сам подтянет свежий код текущей ветки, сделает копию базы, обновит
зависимости и перезапустит сервис. Каталог установки он берёт из systemd, так что
указывать пути не нужно. `.env` и `data/` не трогаются — ключи и кошельки на месте.

Клон потерялся? Достаточно клонировать заново — установка в `/opt` не пострадает:

```bash
git clone -b claude/memecoin-sniper-bot-1nkbtm \
    https://github.com/gytfel/mem-robinhood-and-bnb.git ~/mem-robinhood-and-bnb
cd ~/mem-robinhood-and-bnb && sudo bash scripts/update.sh
```

Если бот стоит не в `/opt/memecoin-sniper` или сервис назван иначе:
`sudo APP_DIR=/свой/путь SERVICE_NAME=своё-имя bash scripts/update.sh`.

**Обновились, а новых команд нет?** Значит служба работает на другом коде — чаще
всего установок оказывается две, бот запущен мимо systemd, или пакет когда-то
поставили обычной установкой и python берёт копию из `site-packages`. Для таких
случаев есть команда, которая приводит сервер в рабочее состояние целиком:

```bash
cd ~/mem-robinhood-and-bnb && sudo bash scripts/deploy.sh
```

`deploy.sh` ничего не предполагает о текущей установке. Он сам находит, где и как
бот запущен (systemd, Docker или вручную), останавливает всё лишнее, ставит код в
тот каталог, откуда бот реально работает, чинит окружение Python, перерегистрирует
службу и **проверяет, что запустился именно новый код** — а не рапортует об успехе.
`.env` и `data/` не трогаются, база копируется в `backups/` перед началом.

Посмотреть, что происходит, ничего не меняя:

```bash
sudo bash scripts/diagnose.sh
```

Скрипт находит работающий процесс и печатает каталог, **из которого тот реально
импортирует код**, плюс состояние systemd, Docker и всех каталогов с установкой.
После обновления бот сам пришлёт в Telegram сообщение о перезапуске, а `/version`
покажет установленный коммит.

Через Docker:

```bash
cp .env.example .env && nano .env
docker compose up -d --build
```

[docs/SETUP.md](docs/SETUP.md).**

## Настройка

Все ключи лежат в `.env`; создать его проще всего командой `sniper init`.
Разбор каждого ключа с картинками шагов — в [docs/SETUP.md](docs/SETUP.md).

### Обязательные переменные `.env`

| Переменная | Что это |
|---|---|
| `BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) |
| `MASTER_KEY` | ключ шифрования приватных ключей. **Потеряете — потеряете все кошельки.** Сгенерировать: `make key` |

### Полезные необязательные

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `ADMIN_IDS` | — | ID администраторов (команда `/stats`) |
| `ALLOWED_USER_IDS` | пусто | белый список; пусто — бот открыт для всех. Меняется на ходу командой `/access`, и её решение важнее этой строки |
| `ENABLED_CHAINS` | из `chains.json` | какие сети включить, например `bsc,robinhood` |
| `BSC_RPC_URLS` | публичные | свои RPC — заметно быстрее снайп |
| `SCANNER_POLL_INTERVAL` | `2.0` | как часто опрашивать новые пары, сек |
| `POSITION_POLL_INTERVAL` | `6.0` | как часто пересчитывать позиции, сек |
| `DEPOSIT_POLL_INTERVAL` | `30.0` | как часто проверять пополнения, сек |
| `SERVICE_FEE_BPS` / `SERVICE_FEE_WALLET` | `0` | комиссия сервиса с покупки (100 = 1%) |

### Сети

Сети описаны в [`config/chains.json`](config/chains.json). **BNB Smart Chain** настроена
сразу (PancakeSwap V2 + Biswap) и работает из коробки.

**Robinhood Chain** — L2 на технологии Arbitrum Orbit. В конфиге лежит заготовка: как
только сеть и её DEX станут доступны, заполните параметры и включите сеть — код менять
не нужно:

```env
RH_ENABLED=true
RH_CHAIN_ID=<chain id>
RH_RPC_URLS=https://<rpc-1>,https://<rpc-2>
RH_ROUTER=0x<адрес Uniswap V2-совместимого роутера>
RH_FACTORY=0x<адрес фабрики>
RH_WRAPPED_NATIVE=0x<адрес обёрнутой нативной монеты>
RH_EXPLORER_URL=https://<обозреватель>
RH_NATIVE_SYMBOL=ETH
ENABLED_CHAINS=bsc,robinhood
```

Пока сеть не заполнена, бот её просто не включает и работает на остальных.

Точно так же добавляется любая другая EVM-сеть — новый блок в `config/chains.json`
(смотрите тест `tests/test_config.py::test_custom_chain_file_is_loaded`).

## Команды бота

**🎯 Снайпинг**

| Команда | Действие |
|---|---|
| `/on` | включить автоснайп (сбрасывает счётчик убытков подряд) |
| `/off` | перестать покупать; открытые позиции продолжают вестись |
| `/dry` | тестовый режим ⇄ боевой: сделки на бумаге по реальным котировкам |
| `/panic` | выключить автоснайп и продать всё; `/panic now` — без подтверждения |
| `/buy <адрес> [сумма]` | купить вручную |
| `/sell <id> [%]` | продать позицию, по умолчанию 100% |
| `/check <адрес>` | полная проверка токена без покупки |

**💼 Кошелёк**

| Команда | Действие |
|---|---|
| `/wallet` | адрес, балансы, пополнение, вывод, экспорт ключа |
| `/balance` | только баланс по всем сетям |
| `/withdraw <адрес> [сумма]` | вывод; «всё» опустошает кошелёк с учётом газа |
| `/newwallet confirm` | создать новый кошелёк (старый ключ теряется) |
| `/import <ключ>` | привязать существующий кошелёк; сообщение с ключом удаляется |

**📊 Позиции и деньги**

| Команда | Действие |
|---|---|
| `/positions` | что открыто, цена входа, текущий P&L |

| `/report` | сводный отчёт **за всё время**: боевые и тестовые сделки рядом, плюсовые и убыточные списками, причины убытков, разбивка по последним периодам + файл со всеми сделками |

## Настройки

**Готовые наборы.** Отдельные настройки легко переставить так, что они спорят
друг с другом: стоп −60% рядом с трейлингом 15% просто выкидывает из каждой
сделки. `/preset` применяет проверенную связку одной командой:

| Набор | Для чего |
|---|---|
| `/preset careful` | мало сделок, жёсткие фильтры, ранняя фиксация — «не терять» важнее, чем «поймать икс» |
| `/preset momentum` | ставка на перехват разгона: мягче пороги входа, покупка по факту движения |
| `/preset aggressive` | много сделок, широкое проскальзывание, поздняя фиксация — расчёт на редкие крупные иксы |

После каждого старта бот сам пишет в Telegram — сразу видно, обновился он или

```

Ветка: main
Код: 82fffaa1 → 9f31ac2b

```

Сообщение уходит администраторам из `ADMIN_IDS` (если их нет — всем
пользователям); отключается настройкой `/set restart off`. Версию и историю
запусков можно посмотреть в любой момент командой `/version`, а `/health`
показывает аптайм и число аварийных завершений подряд.

Коммит определяется из git, а на сервере — из файла `BUILD`, который пишут
`scripts/install-server.sh` и `scripts/update.sh`. В Docker его можно передать
переменными `SNIPER_BUILD_COMMIT` и `SNIPER_BUILD_DATE`.

`/version` показывает сборку, **с которой запущен процесс**, а не ту, что лежит
на диске: файл `BUILD` обновление переписывает сразу, а код в памяти меняется
только при перезапуске службы. Если эти сборки разошлись, `/version` прямо пишет
«бот работает на старом коде» и подсказывает команду перезапуска — иначе выходит,
что команда рапортует об успешном обновлении, которого не было.

## Если монеты списались, а позиции нет

Отправленная транзакция — это уже потраченные деньги, поэтому бот её не бросает
ни при каких обстоятельствах:

* **сеть не подтвердила за 3 минуты** — приходит сообщение «транзакция отправлена»
  со ссылкой на сканер, а ожидание продолжается в фоне (до `PENDING_BUY_TIMEOUT`,
  по умолчанию 30 минут). Позиция появится сама, когда транзакция подтвердится;
* **транзакция отклонена сетью** — сделка записывается как неудачная и видна в
  `/logs`, газ учитывается в издержках;
* **токены не пришли** (стопроцентный налог) — тоже записывается, а не исчезает;
* **сбой при записи позиции** — бот прямо сообщает об этом и предлагает команду
  подбора.

**Позиция закрылась как «токены исчезли»?** Продажа никогда не списывает позицию
по одному нулевому ответу ноды: отставшая или подрезанная нода отвечает нулём без
всякой ошибки, а по такому ответу бот вычеркнул бы токены, которые никуда не
девались. Баланс переспрашивается у всех настроенных RPC, и берётся максимум —
занизить баланс нода может, а показать чужие токены ей неоткуда. Позиция
закрывается как утраченная, только когда все ноды согласны, и об этом приходит
отдельное сообщение со ссылкой на кошелёк.

Подобрать позицию по токенам, которые уже лежат на кошельке:

```
/recover                 найдёт сам всё, что лежит без позиции
/recover 0xАдресТокена   подобрать конкретный токен
```

Без аргумента бот сам проходит по токенам недавних сделок и показывает те, у
которых есть баланс, но нет открытой позиции. Так надёжнее: покупок бывает
несколько подряд, адреса похожи, и подобрать не тот токен слишком легко.

Бот прочитает баланс, найдёт пул и заведёт позицию — тейк-профит и стоп-лосс
начнут работать. Если эта позиция раньше была закрыта как утраченная, она
**возвращается той же записью**, с исходной суммой покупки: иначе убыток по старой
записи посчитался бы второй раз. Для нового токена цена входа берётся **текущая** —
сколько было заплачено на самом деле, бот знать не может.

## Где взять адреса Uniswap V3

На `docs.uniswap.org` → **Contract Deployments**, раздел **Uniswap v3**. Нужны три
контракта из списка:

| На странице | Переменная |
|---|---|
| **SwapRouter02** | `V3_ROUTER` |
| **UniswapV3Factory** | `V3_FACTORY` |
| **QuoterV2** | `V3_QUOTER` |

Нажмите на название — строка развернётся в список сетей с адресами.

Две ловушки в этом списке:

* **SwapRouter02, а не SwapRouter.** Просто «SwapRouter» — старая версия, у неё в
  структуре вызова есть `deadline`. Бот умеет обе (`V3_VARIANT=auto` определяет
  сам), но 02 развёрнут гораздо шире;
* **QuoterV2, а не Quoter.** Второй — версия 1, тоже поддерживается, но основная
  для бота — V2.

Остальное из списка для торговли не нужно: `NonfungiblePositionManager` — для
LP-позиций, `V3Migrator`, `TickLens`, `NFTDescriptor`, `Staker`, `Multicall` — не
про свопы.

Префикс переменной зависит от сети: `BSC_` для BNB Smart Chain, `RH_` для
Robinhood Chain. Пример для BNB:

```
BSC_V3_ROUTER=0x…
BSC_V3_FACTORY=0x…
BSC_V3_QUOTER=0x…
```

Нужны **все три**: без любого из них площадка не включится. `WRAPPED_NATIVE` на
этой странице нет — он уже задан для V2 и тот же самый.

**Проверьте перед боем.** Команда подтвердит, что это действительно V3-роутер,
сама достанет фабрику и WETH (сверьте со страницей) и прогонит настоящую
котировку через Quoter:

```bash
sniper discover <V3_ROUTER> --chain bsc --quoter <V3_QUOTER> --token 0xЛюбойТокен
sniper doctor
```

Если сети нет в списке Uniswap — значит они туда не разворачивались, и V3-пулы
там принадлежат форку. Тогда адреса берите в документации форка либо из
транзакции свопа: поле **To** у неё и есть роутер, а на его странице в обозревателе
`factory()` и `WETH9()` дадут остальные два адреса.

## Комиссии сервиса и реферальная программа

Две комиссии, устроенные по-разному:

| Что | Сколько | Когда |
|---|---|---|
| За пополнение | `DEPOSIT_FEE_BPS` (по умолчанию 2%) | один раз с суммы прихода |
| С прибыли | `PROFIT_FEE_BPS` (по умолчанию 5%) | только с того, что сделка заработала сверх вложенного |

**Убыточная сделка не облагается ничем.** Комиссия считается по позиции целиком,
а не по каждой частичной фиксации: ступени лестницы поодиночке выглядят
прибыльными, хотя сделка в сумме может быть в минусе.

**Реферальная программа.** `/ref` выдаёт ссылку вида
`https://t.me/ВашБот?start=ref<id>`. Друг открывает её и нажимает «Старт» —
приглашение засчитано. После `REFERRALS_FOR_FREE_DEPOSIT` приглашённых (по
умолчанию 3) комиссия за пополнение снимается навсегда. Комиссия с прибыли при
этом остаётся.

Привязка делается **один раз и не на себя**: иначе приглашённого можно было бы
перепривязать и накрутить себе бесплатные пополнения.

**Кто не платит:** администраторы из `ADMIN_IDS` — никогда и ничего; и те, кому
владелец выдал освобождение командой `/exempt ID`.

**Комиссия не берётся, если она меньше цены собственной отправки.** Перевод стоит
газа, и на мелких суммах пользователь заплатил бы за пустую транзакцию, а сервис
не получил бы ничего. Порог задаёт `MIN_FEE_GAS_RATIO`.

Пустой `SERVICE_FEE_WALLET` выключает обе комиссии полностью — отправлять их
некуда.

## Газ и сумма входа

Газ — это плата за транзакцию, а **не процент от суммы**. Он одинаков и для входа
в 0.0002, и для входа в целую монету. Поэтому чем меньше сделка, тем большую её
долю забирает сеть:

| Вход | Газ за круг «купил-продал» | Доля |
|---|---|---|
| 0.0002 | 0.00076 | **381%** |
| 0.001 | 0.00076 | **76%** |
| 0.015 | 0.00076 | 5% |

(при цене газа 1.9 gwei и свопе ~200 000 газа)

Пока газ съедает больше нескольких процентов входа, прибыльной торговли быть не
может: даже удачная сделка уходит в минус на комиссиях. `/set buy` сразу считает
эту долю и предупреждает, если сумма слишком мала, а `/stats` показывает издержки
по вашему реальному расходу газа.

**Про «нужно больше, чем сумма покупки».** Сеть требует, чтобы на балансе лежало
`сумма + лимит газа × цена газа` — лимит, а не фактический расход. Бот проверяет
баланс по газу **собранной транзакции**, а не по значению `/set gaslimit`: этот
параметр всего лишь потолок, и своп тратит впятеро меньше. Иначе бот отказывал бы
при живых деньгах на кошельке.

## Почему стоп-лосс закрывает сделку в −100%

Стоп-лосс срабатывает на первой цене, которую бот увидел ниже порога. Если
ликвидность вынимают одной транзакцией, промежуточных цен между −30% и −100%
просто не существует: в одном блоке пул полон, в следующем пуст. Никакая частота
опроса этого не меняет.

Что бот делает с этим:

* **защита от слива вооружается в момент покупки** — ликвидность пула
  запоминается сразу, а не при первой проверке монитора. Раньше самый быстрый
  слив, сразу после входа, проходил незамеченным: максимум ликвидности был ещё
  нулевым, и правило молчало;
* **такой выход называется «обвал цены», а не «стоп-лосс»** — в уведомлении и в
  отчётах. Стоп с уровнем −30%, закрывший сделку в −100%, выглядит поломкой, хотя
  сработал ровно как задумано;
* **сбой RPC больше не считается сливом.** Раньше ошибка при чтении пула давала
  «ликвидность = 0», и живая позиция продавалась целиком из-за сетевой помехи.
  Теперь неизвестная ликвидность — это «не знаю», и правило пропускает ход.

Предотвращается это только на входе: `/set lpburn 50`, `/set minliq 5`,
`/set rugguard 25`. Разбор в `/report` показывает, сколько именно стоят такие
сделки и каким был бы итог без них.

## Из чего сложился результат: разбор в /report и /pnl

Общий минус не подсказывает, что менять. Разбор показывает, **где именно уходят
деньги** — по причинам выхода и по деньгам, а не по числу сделок:

```
🔴 Убытки (42 сдел. · −0.202 ETH)
   · обвал до нуля (стоп не успел): 12 сдел. · −0.120 (59% всех убытков)
   · стоп-лосс: 25 сдел. · −0.078 (38%)
   · позиция не росла: 5 сдел. · −0.005 (2%)

🟢 Прибыли (28 сдел. · +0.216 ETH)
   · тейк-профит: 8 сдел. · +0.146 (68% всей прибыли)
   · ступень фиксации: 20 сдел. · +0.070 (32%)

Что должно измениться
При винрейте 40% средняя прибыль должна быть не меньше 0.0076 ETH
(сейчас 0.0056 — не хватает 37%).
```

Сделки, закрытые в −90% и глубже, выделяются отдельной строкой. Смешанные с
обычными стопами, они выглядят той же причиной, хотя лечатся совсем иначе:
стоп-лосс от них не спасает — ликвидность вынимают одной транзакцией, и цена
обваливается между проверками. Отчёт считает, каким был бы итог без них, и
предлагает менять не выходы, а фильтры входа (`lpburn`, `minliq`, `rugguard`).

Именно поэтому строки ранжируются по деньгам: десять мелких стопов и одна дыра
в −100% в списке выглядят одинаково, а стоят по-разному.

## Винрейт: почему цель «45% плюсовых» сама по себе ничего не значит

Винрейт — это ручка, а не результат. Поставьте тейк +10% и стоп −80%, и плюсовых
сделок станет большинство: почти любой токен успевает подрасти на 10%. Счёт при
этом будет таять, потому что редкие стопы съедят все победы.

Работает только одно уравнение — ожидание на сделку:

```
ожидание = доля побед × (тейк − издержки) − доля проигрышей × (стоп + издержки)
```

Отсюда следует, какой тейк нужен, чтобы стратегия с заданным винрейтом хотя бы
не теряла деньги:

```
тейк ≥ (1 − винрейт) / винрейт × (стоп + издержки) + издержки
```

Для 45% плюсовых при стопе −25% и издержках 8% это **+48%**. Тейк ниже — и 45%
винрейта будут убыточными. Именно поэтому «просто поднять винрейт» не является
целью: цель — положительное ожидание.

`/winrate 45` считает это на **ваших** данных: перебирает пары тейк/стоп по всем
пулам, которые прошли ваши фильтры, и показывает, какие дают нужную долю плюсовых
и что при этом с ожиданием.

```
🎯 Как получить 45% плюсовых сделок
по 600 пулам, прошедшим фильтры · издержки круга 8.0%

   при стопе −20%  →  тейк не ниже +42%
   при стопе −30%  →  тейк не ниже +54%

🟢 TP +50% / SL −20% · плюсовых 41–48% · ожидание +3.1…+9.4% на сделку
🟡 TP +40% / SL −20% · плюсовых 45–52% · ожидание −0.8…+5.2% на сделку
```

Издержки берутся из вашего реального расхода газа плюс комиссии DEX; налоги
токенов у каждого свои, поэтому это нижняя оценка — свою можно задать вторым
числом: `/winrate 45 12`.

**Почему вилка, а не одно число.** Замеры цены дают пик и минимум, но не их
порядок. Там, где сработали бы оба уровня, результат зависит от того, что
случилось раньше, — одно число здесь было бы выдумкой.

Если отчёт пишет «на ваших данных 45% недостижимы», настройка выходов не поможет:
проблема во входах. Тогда смотрите `/stats` — какие фильтры режут растущее.

## Когда торговать: раздел «Когда торговать» в /stats

`/stats` отдельным блоком показывает, в какие часы токены растут чаще:

```
🕐 Когда торговать (доля 2× · UTC · местное)
В среднем по всем часам: 7.5%

🟢 16:00 (19:00)  35.0%  (40 шт)
🟢 21:00 (00:00)  35.0%  (40 шт)
🔴 07:00 (10:00)   5.0%  (40 шт)

Разница между часами значима.
Торговать только в лучшие часы:
/set hours 16,21
По вашему времени это 00,19.
```

Час попадает в рекомендацию, только если он **значимо** лучше остальных суток —
не просто «выше среднего». Половина часов всегда выше среднего, и окно, собранное
по этому признаку, состояло бы из случайных всплесков. Пока разница не прошла
проверку, отчёт прямо пишет «закреплять окно рано» и команду не предлагает.

Чтобы видеть своё время рядом с UTC, задайте сдвиг пояса: `/set tz 3` (Москва),
`/set tz 2` (Берлин), `/set tz -5` (Нью-Йорк).

Когда разница подтвердится, окно закрепляется:

```
/set hours 16-22        торговать только с 16:00 до 22:00 UTC
/set hours 14,16,21     только в эти часы
/set hours off          круглосуточно (по умолчанию)
```

Ограничение действует на все покупки — и снайп новых пар, и перехват разгона.
Часы всегда UTC, чтобы «лучшие часы» из отчёта и окно торговли не разъезжались.

⚠️ Не ставьте окно по часам, пока `/stats` не написал «разница между часами
значима». На малых данных лучшие часы — это случайность, и вы просто отрежете
половину потока без всякой пользы.

## Качество фильтров: /stats

Обычная статистика отвечает, **сколько** токенов отсеяно. Главный вопрос другой:
**правильно ли**. Фильтр, который режет будущие иксы, выглядит в отчётах ровно так
же, как фильтр, который бережёт деньги, — пока не посмотреть, что стало с ценой
дальше. Поэтому бот следит за ценой всех найденных пулов, а не только купленных.

`/stats` показывает:

```
Прошли фильтр (200 шт)          Отклонены фильтром (500 шт)
   медиана пика  1.4×              медиана пика  1.0×
   дошли до 1.5×  38%              дошли до 1.5×  12%
   дошли до 2×    30%              дошли до 2×     5%
   дошли до 5×     4%              дошли до 5×     1%

Вывод
  30% против 5% — фильтры работают: пропущенное растёт чаще отсеянного.
```

Дальше — **каждый фильтр отдельно**: какая доля отсеянных именно им токенов всё
же дошла до 2×, в сравнении с пропущенными.

* 🟢 отсеивает слабое — фильтр приносит пользу;
* 🔴 режет то, что растёт — фильтр отнимает прибыль, стоит ослабить;
* ⚪️ данных мало для вывода.

Плюс разрез **по часам суток** (в какие часы токены растут чаще) и **издержки** —
во что обходится круг «купил-продал» при текущей цене газа и вашей сумме входа.
Если газ съедает больше 5% входа, отчёт скажет об этом прямо.

**Про честность выводов.** Разница долей почти всегда есть просто из-за
случайности. Каждое сравнение проходит проверку значимости (двусторонний тест
двух пропорций, 95%), и там, где данных мало, отчёт пишет «разница в пределах
погрешности» вместо выдуманной находки. Именно поэтому в первые часы работы
многие строки будут ⚪️ — это правильное поведение, а не отсутствие данных.

Наблюдение за ценой идёт вместе с перехватом разгона, то есть при включённом
автоснайпе (`/on`). Первые выводы появляются через несколько часов.

## Перехват разгона: покупка не только новых токенов

Снайп новых пар — ставка почти вслепую: в секунду листинга о токене известен
только код контракта. Режим «перехват разгона» работает с другой стороны — он
покупает токены, которые **уже торгуются и уже растут**, но до того, как рост
станет заметен всем.

Как это устроено:

1. Все найденные пулы попадают в список наблюдения — включая те, что автоснайп
   когда-то отклонил. Причина отказа часто временная: пустой пул наполняется.
   Добавить токен вручную: `/watch 0xАдрес`.
2. Раз в `MOMENTUM_INTERVAL` секунд бот одним запросом `eth_getLogs` собирает
   события `Swap` сразу по всем наблюдаемым пулам. Из них видно всё нужное:
   сколько было сделок, сколько из них покупок и по какой цене прошла последняя.
   Резервы и симуляции для этого не читаются — наблюдение почти ничего не стоит.
3. Замер сравнивается с предыдущим. Пул становится кандидатом, если цена выросла
   **не меньше** `momgain` и **не больше** `mommax`, сделок было хотя бы
   `momtrades`, покупок среди них не меньше `mombuys` процентов, а оборот выше
   `momvol`.
4. Только для кандидатов запускается обычная полная проверка: honeypot, налоги,
   байт-код, доля владельца, ликвидность. Разгон не отменяет фильтров.

Верхняя граница роста — главное отличие от «купить то, что растёт». Токен,
который за окно улетел на 300%, бот не берёт: там уже нет запаса, и покупка
станет выходом для тех, кто зашёл раньше.

```
/set momentum on          включить режим (автоснайп при этом тоже должен быть включён)
/trending                 что разгоняется прямо сейчас и почему проходит или нет
/watch 0xАдрес            добавить токен в наблюдение вручную
/config momentum          все пороги режима
```

Сделки этого режима помечаются источником `momentum`: в отчёте `/report` есть
блок «По способу входа», который показывает раздельно, что приносит деньги —
снайп листингов, перехват разгона или ручные покупки.

## Что бот делает, чтобы шансов было больше

Прибыль никто гарантировать не может — снайпинг мемкоинов остаётся игрой с
отрицательным матожиданием для большинства участников. Бот бьёт по трём
местам, где деньги теряются чаще всего.

**1. Не входить в заведомо проигрышное.** Кроме симуляции покупки и продажи,
перед входом читается байт-код контракта: есть ли в нём чеканка новых токенов,
чёрный список кошельков, остановка торгов; не является ли контракт обновляемым
прокси, код которого подменят после вашей покупки. Плюс распределение
предложения — сколько токенов у владельца и сколько лежит в пуле. И арифметика:
если налоги и комиссии съедают вашу цель по прибыли, вход не имеет смысла
(`/set minedge`).

**2. Не отдавать обратно то, что уже заработано.** Возврат вложенного
(`/set secure 40`) на заданном росте продаёт ровно ту долю, которая возвращает
потраченное вместе с газом: после этой продажи сделка не может закончиться в
минусе, а остаток едет дальше. Ступень лестницы так не умеет — её доля считается
от размера позиции, и продать 40% на +50% значит вернуть 60% вложенного, а не
всё. Дальше уже про прибыль: лестница фиксаций
(`/set tp [[1.5, 40], [3, 30], [10, 30]]` — 40% позиции на ×1.5, 30% на ×3,
30% на ×10) снимает прибыль по частям, стоп в безубыток (`/set breakeven 50`) защищает
остаток, защита от слива ликвидности (`/set rugguard 50`) выходит, когда из пула
вынимают деньги, а таймер (`/set deadtime`) закрывает позиции, которые никуда не
идут. Какой порог возврата подошёл бы вашим сделкам, считает `/report` — по
вашей же истории.

**3. Успевать выйти.** Продажа идёт с повышенным газом и своим проскальзыванием
(`/set exitgas`, `/set exitslip`), при отказе слippage расширяется и попытка
повторяется, а разрешение роутеру выдаётся заранее (`/set preapprove`) — в момент
стоп-лосса лишняя транзакция стоит дороже, чем сэкономленный газ.

**4. Входить туда, где уже что-то происходит.** Перехват разгона
(`/set momentum on`) покупает не листинги, а уже торгующиеся токены в момент,
когда покупки перевешивают продажи, — это факт вместо ставки на удачу. Верхняя
граница роста не даёт зайти на вершине.

**5. Учиться на своих данных.** `/stats` показывает, какие фильтры отсеивают
поток, `/edge` — есть ли у стратегии преимущество или это везение, `/optimize`
подбирает TP и SL, которые дали бы лучший результат на ваших же сделках.
Проверять всё это можно бесплатно в тестовом режиме `/dry`.

## Как это работает

```
Telegram (aiogram)
        │
        ├── handlers ──► Trader ──────────────┐
        │                                     │
фоновые задачи:                               ▼
  PairScanner  ──► SniperEngine ──► safety ──► DEX (Uniswap V2/V3 router)
  MomentumHunter ─┘   (разгон)                 │
  PositionMonitor ─┘  (TP/SL/трейлинг)         │
  DepositWatcher                               ▼
        │                                  ChainClient
        └──────────► SQLite (позиции, настройки, кошельки)   (RPC с failover)
```

- `sniperbot/chain/` — RPC-клиенты с переключением эндпоинтов, ERC-20, роутер DEX, кошельки;
- `sniperbot/sniper/` — сканер пар, перехват разгона, проверки безопасности, исполнение сделок, монитор позиций;
- `sniperbot/bot/` — Telegram-интерфейс;
- `sniperbot/db/` — модели и запросы (SQLAlchemy 2, async).

### Про измерение налогов

Роутер Uniswap V2 в функциях `...SupportingFeeOnTransferTokens` проверяет
`amountOut >= amountOutMin`. Значит, если перебирать `amountOutMin` двоичным поиском и
смотреть, на каком значении вызов перестаёт проходить, — мы узнаём, **сколько токенов
реально придёт** с учётом всех внутренних комиссий токена. Разница с расчётом по
резервам пула и есть налог. Для симуляции продажи бот находит слот хранилища
`balanceOf`/`allowance` перебором и выдаёт «пробнику» токены через `stateDiff` —
всё это без единой реальной транзакции.

Если RPC не поддерживает `state override` (некоторые публичные ноды), проверки
помечаются как недоступные. Поведение задаёт настройка «Требовать симуляцию»: с ней
такие токены не покупаются вовсе.

## Безопасность

- приватные ключи шифруются AES-256-GCM; ключ шифрования выводится из `MASTER_KEY`
  через scrypt, у каждой записи своя соль, к шифротексту привязан ID пользователя (AAD);
- `.env`, база и каталог `data/` исключены из git — не коммитьте их;
- бэкапьте `data/sniper.db` **вместе** с `MASTER_KEY`: по отдельности они бесполезны;
- закрыть бота посторонним можно через `ALLOWED_USER_IDS` в `.env` или командой
  `/access private` прямо в боте (она же открывает его обратно: `/access open`);
- бот не запрашивает у пользователей seed-фразы и не отправляет ключи наружу.

## Ограничения

- поддерживаются Uniswap V2 и совместимые форки (PancakeSwap V2, Biswap) и
  Uniswap V3 (`exactInputSingle`, оба варианта SwapRouter). Uniswap v4 и
  Universal Router не поддерживаются;
- для V3 обязателен адрес **QuoterV2** — без него нет котировок до сделки;
- продажа в V3 приходит в WETH, бот разворачивает её отдельной транзакцией
  (если она не пройдёт, средства останутся в WETH и не потеряются);
- пара, созданная задолго до заливки ликвидности, не теряется: она попадает в
  список ожидания и перепроверяется до `SCANNER_LIQUIDITY_WATCH_MINUTES`;
- сканер работает по логам через `eth_getLogs`, а не по мемпулу —
  на приватном RPC с WebSocket можно получить преимущество в скорости;
- скорость снайпа зависит прежде всего от качества RPC: публичные ноды медленнее.
